새 Firebase 기능 추가 작업 순서

1. data/datasources/remote/firebase_{domain}_datasource.dart 에 메서드 추가
2. domain/repositories/{domain}_repository.dart 에 인터페이스 추가
3. data/repositories/{domain}_repository_impl.dart 에 구현체 추가
4. presentation 에서는 repositoryProvider / viewModelProvider 만 참조

필수 규칙

현재 uid 접근: presentation 에서 uid 필요 시 반드시 currentUidProvider 사용. FirebaseAuth.instance.currentUser 직접 접근 금지.
// ✅ 올바른 방법
import 'package:vybe/core/providers/auth_providers.dart';
final uid = ref.watch(currentUidProvider); // String? (null = 비로그인)
접근 로깅: 모든 datasource 메서드에서 Firebase 호출 전 반드시 logFirebaseAccess() 호출.
import 'package:vybe/core/utils/firebase_logger.dart';

logFirebaseAccess(
  file: 'firebase_{domain}_datasource.dart',
  service: 'Firestore(컬렉션/경로)',
  purpose: '데이터 사용 목적 설명',
);

인증 플로우

로그인 방식별 UID 형식

방식처리Firebase UID 형식시점
카카오Cloud Functions(kakaoLogin) → Custom Tokenkakao:{kakaoId}베타
네이버Cloud Functions(naverLogin) → Custom Tokennaver:{naverId}베타
전화번호Cloud Functions(phoneLogin) → Custom Tokenphone:{phone}베타
본인인증verifyIdentity → 신규 유저 등록Firebase 자동 생성베타
AppleFirebase Auth 직접 처리Firebase 자동 생성이후

전체 흐름

1. 소셜 로그인 SDK → accessToken / identityToken 발급
2. 네이버/카카오: Cloud Functions → Custom Token 발급  |  Apple: Firebase Auth 직접
3. FirebaseAuth.signInWithCustomToken() → Firebase UID 발급
4. Firestore users/{uid} 존재 확인
   • 신규 → 본인인증(verifyIdentity) → 프로필 입력 → users/{uid} 생성 → 홈
   • 기존 → 홈

핵심 규칙

  • accessToken 은 매번 달라지나 네이버ID 불변 → 항상 같은 Firebase UID 생성
  • 본인인증은 로그인 방식이 아닌 신원 확인 수단
  • phone 필드로 중복 가입 방지 (같은 전화번호 재가입 불가)
  • isVerified: false 로 초기 생성 → 본인인증 완료 시 true 로 업데이트

Flutter 네이버 로그인 코드 패턴

// 1. 네이버 로그인 → accessToken
final NaverLoginResult result = await FlutterNaverLogin.logIn();
final String accessToken = result.accessToken.token;

// 2. Cloud Functions 호출 → Custom Token
final callable = FirebaseFunctions.instance.httpsCallable('naverLogin');
final response = await callable.call({'accessToken': accessToken});
final String customToken = response.data['customToken'];
final bool isNewUser = response.data['isNewUser'];

// 3. Firebase 로그인
await FirebaseAuth.instance.signInWithCustomToken(customToken);

// 4. 신규/기존 분기
if (isNewUser) { /* 본인인증 화면 */ } else { /* 홈 화면 */ }

Firestore — 컬렉션 전체 맵

📁 users/{uid} # 사용자 프로필 └── 📁 searchHistory/{historyId} # 검색 기록 📁 clubs/{clubId} # 클럽 (메인) ├── 📁 info/{clubId} # 부가 정보 (지하철·오픈챗·유의사항) ├── 📁 menus/{menuId} # 메뉴 ├── 📁 photos/{photoId} # 사진탭 (카테고리별) └── 📁 reviews/{reviewId} # 인앱 리뷰 📁 favorites/{favoriteId} # 찜 (top-level) 📁 banners/{bannerId} # 홈 배너 📁 promotions/{promotionId} # 배너 상세 콘텐츠 (배너별 사진·본문, 어드민 페이지에서 작성) 📁 vybeRecommendations/{recId} # VYBE 추천 페이지 큐레이션 (clubs 조인) 📁 performances/{performanceId} # 공연 일정 (장르 페이지 — 힙합 등, top-level, clubs 조인) 📁 notices/{noticeId} # 공지사항 (마이페이지 노출, 어드민 페이지에서 작성) 📁 searchLogs/{logId} # 검색 로그 원본 (클라 create만, TTL 14일) 📁 searchTrends/{docId} # 실시간 인기 검색어 스냅샷 (current · fallback 2개 고정) 📁 searchHashtags/{tagId} # 인기 해시태그 큐레이션 (화면 라우팅 포함) 📁 appConfig/{platform} # 앱 버전 정책 (android · ios 2개 고정, 어드민 페이지에서 편집)
자동 집계 필드: favoriteCount · ratingSum · reviewCount · rating 는 Cloud Functions 트리거로만 갱신. 클라이언트 직접 수정 금지.

쿼리: where isActive==true + where publishedAt<=now orderBy publishedAt desc limit 50 → 인덱스 notices(isActive ASC, publishedAt DESC). publishedAt<=now 는 정렬 키와 같은 필드라 기존 인덱스로 그대로 처리된다(추가 인덱스 불필요). isPinned 은 서버 정렬에 넣지 않고 받아온 뒤 메모리에서 위로 올린다 — 공지 건수가 적어 3필드 인덱스를 유지할 이유가 없고, 정렬 규칙을 바꿔도 인덱스 재배포가 필요 없다.
노출 조건 3가지 — ① isActive==true(게시상태) ② publishedAt <= now(게시 시작) ③ endAt == null || endAt > now(게시 종료). 판정은 NoticeModel.isVisibleAt(now) 한 곳에만 두고 목록·단건 조회가 같이 쓴다. 게시중단(isActive=false)이 게시 기간보다 우선 — 기간 안이어도 안 보인다.
⚠ endAt 은 메모리에서 필터한다 — publishedAt 과 다른 필드에 범위 조건을 하나 더 걸면 복합 인덱스가 추가로 필요한데 공지 건수가 적어 얻는 게 없다. 대신 limit 이 종료된 공지까지 세므로 실제 노출 건수가 limit보다 적어질 수 있다.
⚠ 게시 기간은 Rules에 넣지 않는다 — 클라 시계가 서버보다 조금이라도 앞서면 쿼리 범위가 request.time 을 넘어 목록 전체가 permission-denied가 된다. Rules는 isActive 만 막는다(게시중단 공지는 문서 ID를 알아도 못 읽음 / 예약 공지는 ID를 알면 읽힐 수 있으나 앱 경로의 getNotice 가 같은 기준으로 null 처리).
읽음 상태는 저장하지 않는다. users/{uid}/noticeReads 방식은 공지를 열 때마다 write가 발생 → 베타 규모에 과함. 목록의 NEW 배지는 publishedAt 이 7일 이내인지로만 판정(읽기 전용, 저장소 0). 집계 필드 없음 → Cloud Functions 트리거 불필요.

판정 4단계 — ① isMaintenance(점검) ② minVersion 미만(강제) ③ latestVersion 미만(권유) ④ 통과. 판정은 decideVersionAction()(core/utils/version_utils.dart) 한 곳에만 두고 순수 함수로 테스트한다(test/version_utils_test.dart).
비교는 파트 단위 숫자 비교라 1.10.0 > 1.9.0 이 올바르게 나온다(문자열 비교였다면 반대). 빌드번호(+7)·프리릴리스(-beta1)는 무시 — 스토어에 노출되는 건 버전명이므로 핫픽스도 patch를 올려야 게이트가 인식한다.
fail-open — 네트워크 실패·3초 타임아웃·문서 없음·버전 미상은 전부 통과시킨다. 서버 사고로 전 유저 앱이 잠기는 쪽이 업데이트를 한 번 놓치는 것보다 훨씬 큰 사고다. 예외를 삼키는 곳은 VersionCheck 뷰모델 한 곳뿐 — datasource는 그대로 던진다.
강제·점검 화면은 PopScope canPop:false 로 뒤로가기 우회를 막고, 게이트를 AuthGate 위에 둬서 로그인 플로우 뒤로 밀리지 않게 한다. 앱 복귀(AppLifecycleState.resumed)마다 재검사 — 앱을 며칠 켜둔 기기가 강제 업데이트를 영영 피하는 구멍을 막는다.
⚠ Rules에서 read에 auth 조건을 걸지 않는다 — 게이트는 로그인 전에 이 문서를 읽는다. auth를 요구하면 비로그인 유저가 강제 업데이트·점검 안내를 영영 못 받는다.
⚠ Android/iOS 문서를 나눈 이유 — 스토어 심사·배포 시점이 달라 한쪽만 minVersion 을 올릴 수 있어야 한다.

운영 주의사항 — 이 문서는 값 하나로 전 유저를 막을 수 있다

상황해야 할 것 / 하면 안 되는 것
강제 업데이트 켜기새 빌드가 스토어에 실제로 게시된 것을 확인한 뒤 minVersion 을 올린다. 심사 중에 미리 올리면 심사자 기기가 차단 화면에 막혀 리젝된다. 안드로이드 단계적 출시(%) 중이라면 아직 못 받은 유저가 있으므로 100% 도달 후에 올린다
잘못 올렸을 때minVersion 을 빈 문자열로 되돌리면 즉시 해제된다 — 앱 재배포 불필요. 유저 기기에는 다음 앱 실행 또는 백그라운드 복귀(resumed) 시점에 반영된다
반영 시점앱 실행 시와 복귀(resumed) 시에만 조회한다. 앱을 켜 둔 채 화면만 옮기는 동안에는 반영되지 않는다(의도된 동작 — 사용 중 갑자기 차단 화면이 뜨지 않게)
점검 모드isMaintenance=true 는 최신 버전 유저까지 전원 차단한다. 켜기 전에 대상 범위를 확인할 것. 끄면 유저가 '다시 시도' 버튼으로 바로 복귀한다
버전 값 형식"1.2.0" 처럼 숫자·점만. 빌드번호(+7)·프리릴리스(-beta1)를 넣어도 무시되므로 핫픽스도 patch를 올려야 게이트가 구분한다. pubspec.yaml 의 version: 과 스토어 버전명이 일치해야 판정이 맞는다
문서 삭제 금지문서가 없으면 게이트가 항상 통과(fail-open)로 동작해 사실상 꺼진다. 기능을 끄고 싶으면 문서를 지우지 말고 필드를 비운다
storeUrl비어 있으면 Android만 market://details?id={설치된 packageName} 로 폴백한다. iOS는 폴백이 없다 — App Store Connect 등록 후 https://apps.apple.com/kr/app/id{앱ID} 를 반드시 채울 것. 안 채우면 업데이트 버튼이 토스트만 띄운다
오프라인 유저Firestore get() 이 로컬 캐시본을 주거나 3초 타임아웃으로 실패 → 둘 다 통과. 오프라인 상태에서는 강제 업데이트가 걸리지 않는다(의도된 fail-open)
쓰기 권한Custom Claim admin: true 계정만 수정 가능. 어드민 페이지 구축 전까지는 scripts/seed_app_config.js 또는 Firebase 콘솔에서 직접 수정

스케줄 함수 — Cloud Scheduler + Pub/Sub (Blaze 필요)

함수명스케줄역할
cleanupPastPerformances매일 KST 04:00종료된 공연 문서 삭제. startAt < now - 8h(PERFORMANCE_DURATION_HOURS)인 공연만 삭제 → 예정·진행 중(새벽) 공연 보존. 500개씩 배치 삭제
aggregateSearchTrends매시 정각 KST (0 * * * *)검색 로그 집계 → searchTrends/current + searchHashtags.popularityRank. 매시 깨어나 갱신 대상인지 내부 판단하고, 아니면 Firestore 접근 없이 즉시 종료
공연은 startAt(Timestamp) 후 최대 8시간 진행으로 가정(클럽 마감 ~06:00). 8시간 안 지난 공연은 "진행 중"으로 보존 → 오늘 밤 새벽 공연/어제 이어진 공연 안전. date(YYYYMMDD)가 아닌 startAt 기준 삭제가 핵심. 마감 더 늦으면 PERFORMANCE_DURATION_HOURS 상수만 조정.

검색 트렌드 갱신 주기 (scheduleDecision() — functions/src/search/compute_trends.ts)

구간실시간 인기 검색어인기 해시태그
야간 20:00~09:00 (9시 포함)매시매시
주간 10:00~19:002시간 (10·12·14·16·18)4시간 (12·16)
주간 간격은 자정 기준 앵커(hour % N)라 해시태그 갱신 시각은 항상 검색어 갱신 시각의 부분집합 → 로그 스캔 1회로 둘 다 처리한다. 클럽 검색이 밤에 몰리므로 야간을 촘촘하게 잡음. 순수 로직은 compute_trends.ts에 Firestore 의존 없이 분리 — 되먹임 필터·고유유저 집계·증감·fallback·갱신주기 판단 전부 여기 있음.
중복 실행 방어: 스냅샷에 runKey(KST yyyyMMddHH)를 저장해 같은 시각 재실행 시 skip. 안 막으면 증감이 방금 쓴 결과와 비교돼 전부 same으로 뭉개진다.

구현 시 주의사항

자동 집계 필드 직접 수정 금지 — favoriteCount · ratingSum · reviewCount · rating 은 반드시 Cloud Functions으로만 업데이트.
  • ratingSum / reviewCount 증감은 FieldValue.increment() 사용 (동시 요청 정합성)
  • rating 은 트랜잭션으로 ratingSum / reviewCount 계산 후 저장
  • onReviewDeleted 에서 reviewCount 가 0이 되면 rating = 0 처리
  • deleteUser 는 Admin SDK로만 처리 (클라이언트 직접 삭제 불가)
  • 네이버 UID 형식: naver:{naverId}
  • onUserCreated 는 문서가 이미 존재하면 덮어쓰지 말 것 (중복 실행 방어)
  • cleanupPastPerformances 는 date(YYYYMMDD)가 아닌 startAt(Timestamp) 기준 삭제 — 새벽 공연 오삭제 방지. 스케줄 함수라 Blaze 요금제 필요

클럽 검색 (Algolia)

검색은 Algolia 단일 경로. Firebase Extension(firestore-algolia-search)이 clubs 컬렉션을 Algolia clubs 인덱스로 자동 동기화하고, 앱은 Search-Only 키로 관련도순 검색(오타 보정 + prefix 매칭)한다.

clubs 쓰기 → Extension → Algolia `clubs` 인덱스 자동 동기화 // objectID = doc.id(= clubId) 앱 검색 → algolia_club_search_datasource // Search-Only 키 → 관련도순 clubId 페이지 (10개씩, page 번호 커서) → clubId로 Firestore getClub 조인 // 인덱스엔 표시용 일부 필드만
  • Extension 설정: Collection Path clubs, Index clubs, Indexable Fields: name,area,genre,genreStyles,tags,address,rating,thumbnailUrl,entryFeeMin,isActive,favoriteCount
  • 진입점 ClubRepositoryImpl.searchClubsPage 하나 — viewmodel/화면은 엔진 무관
  • 비활성 클럽 제외는 조인 후 isActive 재확인으로 처리 — Algolia filters는 attributesForFaceting 미선언 속성이면 조용히 0건이라 사용 안 함
  • .env 키: ALGOLIA_APP_ID / ALGOLIA_SEARCH_API_KEY — 없으면 검색 결과 빈 값
키 규칙 — 앱에는 Search-Only 키만. Admin/Write 키는 Extension(서버)에서만 사용.
구 B안(Firestore searchTokens 검색)은 폐기 (2026.07.19) — onClubWritten 트리거·clubs.searchTokens 필드·전용 복합 인덱스 전부 삭제됨 (정리 스크립트 scripts/remove_search_tokens.js).
