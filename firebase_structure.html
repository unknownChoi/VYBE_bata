전체 흐름

1. 소셜 로그인 SDK → accessToken / identityToken 발급
2. 네이버/카카오: Cloud Functions → Custom Token 발급  |  Apple: Firebase Auth 직접
3. FirebaseAuth.signInWithCustomToken() → Firebase UID 발급
4. Firestore users/{uid} 존재 확인
   • 신규 → 본인인증(verifyIdentity) → 프로필 입력 → users/{uid} 생성 → 홈
   • 기존 → 홈

핵심 규칙

  • accessToken 은 매번 달라지나 네이버ID 불변 → 항상 같은 Firebase UID 생성
  • 본인인증은 로그인 방식이 아닌 신원 확인 수단
  • phone 필드로 다른 방식의 중복 가입 방지 — 같은 번호라도 가입할 때와 같은 방식이면 로그인은 허용한다. 전화번호 주인 판정
  • isVerified: false 로 초기 생성 → 본인인증 완료 시 true 로 업데이트

Flutter 네이버 로그인 코드 패턴

// 1. 네이버 로그인 → accessToken
final NaverLoginResult result = await FlutterNaverLogin.logIn();
final String accessToken = result.accessToken.token;

// 2. Cloud Functions 호출 → Custom Token
final callable = FirebaseFunctions.instance.httpsCallable('naverLogin');
final response = await callable.call({'accessToken': accessToken});
final String customToken = response.data['customToken'];
final bool isNewUser = response.data['isNewUser'];

// 3. Firebase 로그인
await FirebaseAuth.instance.signInWithCustomToken(customToken);

// 4. 신규/기존 분기
if (isNewUser) { /* 본인인증 화면 */ } else { /* 홈 화면 */ }

기능 설계 — 공통 원칙

이 아래 섹션들은 기능별로 "왜 이렇게 짰는지"를 정리한다. 컬렉션 스키마는 Firestore 섹션, 함수 시그니처는 Cloud Functions 섹션에 있고, 여기서는 동작 흐름과 판단 근거만 다룬다.

원칙뜻적용된 곳
판정은 순수 함수 한 곳조건 분기는 Firestore·화면과 분리된 순수 함수에 몰아넣고 단위 테스트로 고정. 화면은 결과만 본다version_utils.dart · session_utils.dart · app_geo.dart · compute_trends.ts · NoticeModel.isVisibleAt
fail-open확인에 실패하면 막지 말고 통과시킨다. 서버 사고·오프라인으로 전 유저 앱이 잠기는 쪽이 훨씬 큰 사고버전 게이트 · 네트워크 게이트 · 세션 검사 · 위치 조회
집계 필드는 서버만 쓴다rating·reviewCount·favoriteCount는 Cloud Functions 트리거 전용. 클라는 읽기만리뷰 · 찜
노출 제어는 문서 삭제가 아니라 플래그지우면 되돌릴 수 없고 집계가 어긋난다. isActive·isHidden·기간 필드로 숨긴다탈퇴 · 공지 · 배너 · 클럽
앱 배포 없이 바꿀 수 있게문구·링크·정책값은 코드가 아니라 Firestore 문서에 둔다appConfig · notices · searchHashtags
SDK는 datasource 한 곳Firebase뿐 아니라 GPS·네트워크·설정앱 SDK도 전용 datasource 안에만 둔다. presentation은 provider만 본다device_location_datasource · device_network_datasource

앱 시작 게이트 체인 구현 완료

앱 실행 시 홈에 닿기까지 4개의 게이트를 순서대로 통과한다. 순서가 설계의 핵심이다.

runApp │ ├─▶ SplashGate # 스플래시 연출(min 2.6s / max 5.5s) + GPS 1회 조회 │ ├─▶ NetworkGate # 연결 없음 → 안내 화면 (fail-open) │ ├─▶ VersionGate # 점검 / 강제 업데이트 / 권유 (fail-open) │ └─▶ AuthGate # 세션 판정 → MainScaffold 또는 WelcomeScreen
순서왜 이 자리인가
NetworkGate 가 VersionGate 위연결이 없으면 버전 조회·세션 복원은 타임아웃만 먹고 빈 화면이 된다. 원인을 먼저 알려야 한다
VersionGate 가 AuthGate 위강제 업데이트·점검은 로그인 전에 걸려야 한다. 그래서 appConfig Rules에 auth 조건을 걸지 않는다 — 걸면 비로그인 유저가 안내를 영영 못 받는다
네트워크 확인이 스플래시 중에 시작splashDestinationProvider 가 networkStatusProvider 를 보기 때문에 연출과 병렬로 돈다 — 대기 시간이 겹쳐 사라진다

세 게이트 전부 fail-open — 조회 실패·타임아웃·문서 없음은 모두 통과다. 게이트는 차단 장치가 아니라 안내 장치로 설계했다.
재검사 시점 — 버전·세션·네트워크 모두 AppLifecycleState.resumed(앱 복귀)에 다시 본다. 앱을 며칠 켜 둔 기기가 강제 업데이트를 영영 피하는 구멍을 막기 위함. 사용 중 화면만 옮기는 동안엔 재검사하지 않는다 — 쓰던 중 갑자기 차단되면 안 되므로.

자동 로그인 / 세션 유지 구현 완료

구현 완료 (2026.08.16) — 판정은 core/utils/session_utils.dart(순수 함수) + presentation/auth/viewmodels/session_viewmodel.dart(SessionCheck) 두 곳에만 있다. flutter analyze 경고 0 · 단위 테스트 9건 통과.

현재 상태 — 자동 로그인은 이미 동작한다

Firebase Auth 는 네이티브(Android · iOS)에서 세션을 디스크에 저장하므로 앱을 껐다 켜도 로그인은 이미 유지된다. AuthGate 가 authStateChanges 를 구독해 uid 유무로 진입 화면을 가르는 구조가 이미 있다. 따라서 새로 만들 "자동 로그인 기능"은 없고, 자동 로그인이 상시 켜진 상태에서만 드러나는 구멍을 막는 것이 실제 작업 범위다.

막아야 할 구멍 4가지

#구멍원인 / 근거
1 유령 세션
Firebase 로그인은 됐는데 프로필 미완성		 certification_number_handler.dart 의 finalizeLogin()(세션 성립) → saveUserProfile() 사이에서 앱 종료·네트워크 실패 시 세션만 남는다.
⚠ onUserCreated 트리거가 users/{uid} 를 uid·provider·타임스탬프만으로 먼저 만들기 때문에 문서 존재 여부로는 판별 불가 — 판정 기준은 isVerified
2 isNewUser 오판 naverLogin/kakaoLogin 이 돌려주는 isNewUser 는 Auth user 존재 여부일 뿐 프로필 완성과 무관. 미완성 유저가 재로그인하면 isNewUser=false → 앱이 그대로 홈으로 보낸다
3 죽은 계정 다른 기기에서 탈퇴하거나 Auth user 가 비활성화돼도 로컬 세션은 살아 있다. 자동 로그인이라 재로그인 시점이 없어 영영 감지되지 않을 수 있다
4 소셜 SDK 세션 잔존 signOut() 이 Firebase 세션만 정리한다. 카카오·네이버 SDK 세션이 남아 재로그인 시 계정 전환이 불가능

세션 판정 — 단일 소스

판정은 순수 함수 decideSessionAction()(core/utils/session_utils.dart) 한 곳에만 있다. version_utils.dart 와 같은 패턴.

SessionAction조건결과
noneuid 없음WelcomeScreen
keepuid 있음 + isVerified == true
(또는 users 조회 실패 — fail-open)		MainScaffold
signOut자동 로그인 OFF
또는 isVerified == false · 문서 없음(유령 세션)
또는 토큰 갱신이 서버에서 거부됨		세션 정리 → WelcomeScreen

화면(AuthGate)이 보는 것은 SessionCheck 의 결과 두 가지(ready / signedOut)뿐이다. 검사가 끝나기 전에는 스플래시를 유지한다 — 검사 중 WelcomeScreen 을 잠깐 그리면 멀쩡히 로그인된 사용자에게 로그인 화면이 번쩍인다.

검사는 콜드 스타트 1회 + 복귀 시 토큰만 — 검사가 끝난 뒤로는 AuthGate 가 uid 하나로만 라우팅한다. 앱 실행 중에 프로필 완성 여부를 다시 판정하면, 본인인증(외부 앱·웹뷰) 을 다녀오거나 프로필 저장 직전인 사용자를 로그아웃시킨다. 복귀(resumed) 시에는 서버 무효화 여부만 다시 확인한다.
fail-open 원칙 — users/{uid} 조회 실패·3초 타임아웃은 전부 ready 로 통과시킨다. 오프라인 사용자를 로그인 화면으로 튕기는 쪽이 훨씬 큰 사고다. VersionGate 와 동일한 원칙.
미완성 세션은 가입 재개가 아니라 signOut — 세션을 살린 채 본인인증 화면으로 직행시키면 뒤로가기·중도 이탈 경로를 전부 따로 처리해야 한다. 유령 세션을 즉시 정리하고 Welcome 부터 다시 태우는 쪽이 단순하고 안전하다 (사용자는 소셜 버튼 한 번 더 누르면 본인인증으로 이어짐).

고쳐진 버그 — 본인인증으로 가입한 계정(phone:010-…)이 로그아웃 후 같은 방식으로 다시 로그인하면 이미 존재하는 계정입니다. 로 막혀 영영 못 들어왔다. checkPhoneDuplicate 가 bool 하나만 돌려줘 "번호 있음 = 무조건 차단"이었기 때문. 이 방식에는 재로그인 경로 자체가 없었다.

별도의 '탈퇴 철회' 버튼을 두지 않았다 — 로그인이 곧 복구다. 되돌아온 사용자가 하는 행동은 어차피 로그인이고, 철회 화면을 따로 만들면 탈퇴 대기 계정에게만 보이는 로그인 앞 단계를 하나 더 유지해야 한다.

왜 그렇게 했나이유
토큰 발급 전에 복구Auth 계정이 disabled 인 채로 토큰을 주면 앱의 signInWithCustomToken 이 auth/user-disabled 로 거부된다
purgeAt 이 지났으면 안 살린다되살려 놔도 그날 새벽 purgeDeletedUsers 가 데이터를 지운다. 이때 purgeAt 을 null 로 보내는 것도 의도 — 이미 지난 날짜를 "그날부터 가입 가능"이라 안내하면 거짓말이다
상태 필드를 맨 마지막에 지움중간에 실패하면 status 가 pendingDeletion 으로 남아 다음 로그인이 처음부터 다시 시도한다. 각 단계가 isHidden==true 인 문서만 손대므로 재실행해도 이중 가산이 없다(숨김 쪽과 대칭)
가산 주체도 함수 하나isHidden 을 false 로 되돌리는 것도 update 라 onReviewUpdated 가 발화한다. 그 트리거는 isHidden 전이를 양방향 모두 건너뛰게 돼 있어 그대로 재사용된다 — 가드를 추가할 필요가 없었다
Storage 손댈 것 없음탈퇴는 파일을 지우지 않고 숨기기만 했다. 파기 단계에서만 삭제한다
checkPhoneDuplicate 를 같이 고치지 않으면 복구까지 도달하지 못한다 — 본인인증 경로는 로그인 전에 번호 주인을 먼저 묻고, 예전 규칙(!pending && ...)에선 본인이어도 sameAccount=false 라 화면에서 먼저 막혔다. 이제 본인 + 파기 전이면 sameAccount=true·pendingDeletion=false·restorable=true 로 통과시킨다.
앱 안내 — 복구는 조용히 일어나면 안 된다(사용자가 탈퇴가 취소된 걸 모른다). 본인인증 경로는 인증 화면으로 넘어가기 전 kAccountRestoreNotice 로 예고하고, 복구가 끝나면 kAccountRestoredMessage 토스트를 띄운다(소셜은 WelcomeScreen, 본인인증은 인증번호 화면). 문구 상수는 presentation/auth/signup_flow.dart 한 곳. 탈퇴 화면의 타임라인·완료 오버레이 문구도 "보관 기간엔 로그인도 막힌다" → "다시 로그인하면 복구된다"로 고쳤다 — 새로 가입하는 것은 여전히 파기일 이후다.

시간대별 무료입장 데이터 · 홈 섹션 완료 나머지 화면 미적용

요구는 둘이다 — ① 일정 시간대에는 입장비가 무료인 클럽이 있다 ② 그 시간이 아니면 일반 입장비. 지금 스키마엔 시간축이 없어 entryFeeMin == 0 하나로 '무료'를 표현하고 있고, 이 값은 켜면 24시간 무료다. 그래서 필드를 하나 더 얹는 게 아니라 의미를 갈라야 한다.

결정이유

미니맵 비율 — cols : rows

클럽마다 홀 모양이 다르다 — 세로로 긴 곳도, 가로로 긴 곳도 있다. 셀이 정사각이므로 칸 수의 비가 곧 앱 미니맵 모양이 되고, 따로 aspectRatio 필드를 둘 필요가 없다.

결정이유

층·구조물·테이블·등급을 한 문서에배치도는 통째로 편집되고(여러 개 옮기고 한 번 저장) 통째로 읽힌다. 쪼개면 앱은 read N회, 웹은 저장이 원자적이지 않아 저장 도중 반쯤 옮겨진 배치도가 앱에 보인다
1MB 한도 걱정 없음테이블 50개 + 구조물 15개여도 20KB 미만
쓰기는 문서 전체 교체(set)부분 update 를 허용하면 지운 테이블이 남는다. 웹은 commit + updateMask 없는 update 로 쓴다
schemaVersion 을 둔다앱이 모르는 판(> 1)이면 렌더를 포기한다. 모르는 필드를 억지로 그리면 깨진 화면이 나온다

색·타입은 키만 저장

colorKey(purple·blue·lime·pink·amber·gray)와 fixture.type 은 영문 키만 저장하고 실제 색·아이콘·라벨은 앱이 갖는다(ClubFacility·provider·gender 와 같은 규칙). 업주가 hex 를 자유 입력하게 두면 다크 배경에 안 보이는 색이 나오고, 앱 테마를 바꿀 때 전 클럽 문서를 손봐야 한다. 앱이 모르는 fixture.type 은 조용히 버린다 — 영문 키가 화면에 뜨는 것보다 안 그리는 편이 낫다.

금액은 숫자로

구 상수는 price: '100만', minSpend: '1,000,000원' 문자열이었다. 업주가 100만원/100만/1000000 을 제각각 입력하면 정렬·비교·필터가 전부 불가능해진다 → price: 1000000 (원 단위 int). 표기는 presentation/common/table_price_format.dart 한 곳에서 만든다. 0 은 무료가 아니라 '문의' — 테이블은 공짜로 주는 상품이 아니다.

권한 — 파트너 커스텀 클레임

업주 계정 클레임 : { partner: true, clubIds: ["abc123", "def456"] } Rules clubs/{clubId}/tableLayout/{docId} read : 누구나 write : admin 또는 (partner == true && clubId in token.clubIds) + request.resource.data.clubId == clubId + schemaVersion is number
is int 가 아니라 is number 다. 클라 SDK 가 숫자를 double 로 실어 보내면 is int 는 업주의 모든 저장을 거부한다. 이건 보안 경계가 아니라 형식 가드일 뿐이라 넓게 받고, 실제 판정은 앱 파서가 한다.
규칙이유
token.get('clubIds', []) 로 읽는다클레임에 키가 없는 계정에서 직접 접근하면 Rules 평가가 에러로 떨어져 통째로 거부된다(isHidden 때와 같은 함정)
셀 좌표·배열 원소는 Rules 로 검증하지 않는다Rules 에는 반복문이 없어 배열 안 객체를 못 훑는다. 소유권·clubId 일치만 막고 값 검증은 파트너 웹 입력단 + 앱 파서가 한다
앱 파서가 격자 밖 값을 clamp 한다격자를 나중에 줄였거나 잘못된 문서가 들어와도 화면 밖에 그리지 않는다. 1×1 테이블은 2×2 로 키운다
권한 회수는 즉시 반영되지 않는다. 커스텀 클레임은 ID 토큰에 박혀 있어 clubIds 에서 클럽을 빼도 그 업주의 기존 토큰이 만료될 때까지(최대 1시간) 쓰기가 통과한다. 계약 해지처럼 즉시 끊어야 하면 revokeRefreshTokens + Rules 의 auth_time 검사가 필요하다 — 지금 단계에서는 과해서 제약만 남긴다. 클레임 전체는 1000바이트 제한이라, 업주 한 명이 클럽 수십 곳을 갖는 구조가 되면 clubs.ownerUids + Rules get() 방식으로 옮겨야 한다(그때는 Rules get 이 read 1회로 과금된다).

업주 웹이 지켜야 할 계약

  1. 저장은 문서 통째로 set() — 부분 update 금지(원자성이 이 설계의 핵심)
  2. 테이블끼리 셀 겹침 금지. 구조물은 겹쳐도 된다(앱이 구조물을 먼저 그리고 테이블을 위에 얹는다)
  3. 격자 밖 금지 — col + colSpan <= cols, row + rowSpan <= rows
  4. 테이블 최소 2×2, 구조물 1칸 허용. cols 4~14, rows 4~32
  5. 테이블은 방 안에만 — cells 로 도려낸 칸을 밟으면 앱에서 허공에 뜬다. 구조물은 경계에 걸쳐도 된다
  6. 물건(테이블·구조물)이 놓인 칸은 방 밖으로 못 뺀다
  7. cells 길이는 항상 cols × rows. 격자를 바꾸면 마스크도 같이 옮긴다(remap) — 길이가 어긋나면 앱이 통째로 버린다
  8. 비율은 cols : rows 로만 정한다. 별도 aspectRatio 필드를 만들지 않는다
  9. id 는 층 안에서 유일. 기존 테이블 id 를 바꾸지 않는다
  10. 금액은 원 단위 정수만
  11. schemaVersion: 1 고정
  12. cols·rows 를 줄일 때 밖으로 밀려나는 항목이 있으면 저장을 막는다 — 앱은 clamp 하지만 그 결과는 업주가 의도한 배치가 아니다

자동 집계 필드 직접 수정 금지 — favoriteCount · ratingSum · reviewCount · rating 은 반드시 Cloud Functions으로만 업데이트.
  • ratingSum / reviewCount 증감은 FieldValue.increment() 사용 (동시 요청 정합성)
  • rating 은 트랜잭션으로 ratingSum / reviewCount 계산 후 저장
  • onReviewDeleted 에서 reviewCount 가 0이 되면 rating = 0 처리
  • 네이버 UID 형식: naver:{naverId}
  • onUserCreated 는 문서가 이미 존재하면 덮어쓰지 말 것 (중복 실행 방어)
  • cleanupPastPerformances 는 date(YYYYMMDD)가 아닌 startAt(Timestamp) 기준 삭제 — 새벽 공연 오삭제 방지. 스케줄 함수라 Blaze 요금제 필요

검색은 Algolia 단일 경로. Firebase Extension(firestore-algolia-search)이 clubs 컬렉션을 Algolia clubs 인덱스로 자동 동기화하고, 앱은 Search-Only 키로 관련도순 검색(오타 보정 + prefix 매칭)한다.

    ⚠ 배포본은 아직 19개 (2026.09.01 실측 — 위 18개 + 삭제된 genreStyles). 앱 _requiredFields 엔 genreStyles 가 없어 동작엔 영향 없고, 다음 설정 변경 때 같이 뺀다
